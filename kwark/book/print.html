Kwark

Introduction

Kwark is a terminal-based text-editor “framework”. By framework, I mean that kwark doesn’t just “run” on its own, you must use it as a library in your own rust “project” (kwark calls these flavors).

This is a very different approach to lots of “applications” that come around in the editing community. However, I think that this model works incredibly well, as I am able to accomplish a lot of integration with users that I wouldn’t be able to otherwise.

Goals of this Project

  • Be a fully configurable, well featured text-editor
  • Support rust as both a plugin-manager and configuration system
  • Be easy to understand and customize to your own usecases

Why Rust

Well, for starters, rust is a very fun language to write in. In my personal opinion, I don’t care all that much about it being “fast”, or “memory-safe” (though those things are awesome). I care much more about how fun a language is to use, and how much effort I would want to put in to know that language better, and rust hit both of those points for me.

Why No Scripting Language

Rust is an amazing language, and I like using it to do things. As well, making kwark a framework was not a light choice.

  • I have gone through multiple iterations of this project, before, it was named Kerbin, and I wrote a light “shell-style” language for it, and it just felt too out of place.
  • I have messed with using rune for projects, but again, little editor support (no lsp), and it was just not worth learning.

So, after multiple iterations, I asked myself, why not just use rust, I had tried it in Kerbin, but it failed because I was trying to do it over FFI (not easy while keeping the type system nice). This lead me to the decision of turning my new implementation of my editor (kwark) into a framework, and having your configuration just be the application that pulls in the framework.

This gave me access to all of the type-system guarentees I was missing from lua, the strong editor-integrations I was missing in rune, and the nice-feeling of use that none of them gave me.

What about compile times?

Yes, I know that rust compile-times can get quite slow, and that is definitely a worry of mine, however, rust’s incremental compilation is quite fast, and is able to skip a lot of work most of the time, so see for yourself, but I rarely see myself changing the configuration enough to care about <10 seconds of compilation here and there.

Installation

  • Create a new cargo project somewhere.

  • Add kwark as a git dependency

    • Use cargo add kwark --git https://github.com/TheEmeraldBee/kwark in order to add the framework as a dependency

  • Add anyhow as a dependency

    • Use cargo add anyhow to add anyhow to your project

Where to put the project

While there is no required place to put the project, as kwark is just a library you use to build the editor yourself, I would recommend using cargo new kwark in your ~/.config/ directory so that kwark’s “configuration” exists in a common place for configurations to exist.

Project template

Below is a very basic example project that just creates a binding that, on ctrl-c being pressed, the editor exits

use kwark::prelude::*;

// The state of this editor, with no plugins
#[kwark::state]
pub struct MinimalState {}

fn main() -> anyhow::Result<()> {
    // Build the editor and register every plugin in the state
    let mut editor = kwark::init::<MinimalState>()?;

    // The "normal" mode is the mode the editor starts in
    let normal = editor.core.input.tree("normal");

    // Here, we'll create a binding for the key `ctrl-c`,
    // and we'll give it the description "Quit".
    //
    // The closure below takes in the editor, does something, and returns a result in case we want to return an error
    //
    // We must "try" this method, as the string "ctrl-c" is a shorthand to writing a binding, and it can fail if you put bad text.
    //
    // If the binding is invalid, our editor will crash before it even runs, and end up doing nothing :)
    normal.bind(&["ctrl-c"], "Quit", |e| {
        e.core.running.quit();
        Ok(())
    })?;

    // Create a new buffer and insert it into our **global** buffer list
    // This won't show the buffer, we're just telling the editor that the buffer should exist with this info
    let id = editor
        .core
        .buffers
        .insert(text::BufferEntry::new_scratch("instructions"));

    // This line is what tells the **active** split/window to show the given buffer ID in our frame-loop
    editor.core.windows.active_mut().select(id);

    // Let's insert some text into our just created buffer
    //
    // This is a little bit of work, but it's because even though above we guarenteed the buffer exists,
    // all methods in the `core` are built to assume nothing, but because we're sure, let's just use `.expect()` here
    editor
        .core
        .active_buffer()
        .expect("Just set to something")
        .as_text()
        .expect("Should be text buffer")
        .insert("Press `ctrl-c` to exit :)", &text::CursorOptions::new());

    // Run until a binding quits the editor
    kwark::run(editor);

    // We get control back afterwards
    println!("Thank you for using kwark!!!");

    Ok(())
}

Plugins

What is a plugin

It is a rust struct that implements a trait that can be added to your project, often coming from external sources (hence the name plugin)

Why support plugins

While the editor I primarily use, helix, has been in debate around this for a very long time, I already know what I want kwark to be, as EXTENSIBLE as possible, while still having a good core (much like nvim). So, plugins are a must-have, and make for a reasonable, and simple abstraction for people to use to add things.

Plugins are also a great way of allowing me to handle the desire for me to add “built-in” features that many people but not all would want.

How do I create a plugin

Plugins are farily simple to create, but are slighly hard to understand initially, because in order to maintani strong type safety and discoverability, Kwark utilizes a macro in order to store the state for each plugin

Plugins require us to implement 2 traits:

  1. kwark::PluginState - This is the trait that tells the editor what the plugin’s state needs to be, as well as providing a function in order to create it.
  2. kwark::Plugin - This is the trait that, given a state, tells the editor how we use it.

It makes more sense when looking at the following example:

use kwark::prelude::*;

/// A basic plugin that prints its state when it's registered
pub struct MyPlugin {
    initial: bool,
}

impl kwark::PluginState for MyPlugin {
    // Put any state type here, this is what you can use wherever
    type State = bool;

    fn init(&self) -> anyhow::Result<Self::State> {
        // must run and return a valid state from the editor
        Ok(self.initial)
    }
}

impl<S: Has<MyPlugin> + 'static> kwark::Plugin<S> for MyPlugin {
    // This method runs once **after** our state is created, this should be used to make the plugin be prepared to work, IE: when events occur
    fn register(&self, editor: &mut Editor<S>) -> anyhow::Result<()> {
        // This is how we access the data from our plugin. Without the `Has<MyPlugin>` above, this line wouldn't compile!
        let state = editor.plugin::<MyPlugin>();

        // For this example, let's just print out our state's value :)
        println!("My Plugin Is Registered with data, and it's initial is set to: {state}!");

        Ok(())
    }
}

#[kwark::state]
struct MyState {
    #[plugin(MyPlugin { initial: true })]
    my_plugin: MyPlugin,
}

fn main() -> anyhow::Result<()> {
    // Initialize the editor, this will also register our plugin!
    let mut editor = kwark::init::<MyState>()?;

    // Bind a quit control
    editor
        .core
        .input
        .tree("normal")
        .bind(&["ctrl-c"], "Exit", |s| {
            s.core.running.quit();
            Ok(())
        })?;

    // Insert a new scratch buffer
    let id = editor
        .core
        .buffers
        .insert(text::BufferEntry::new_scratch("instructions"));

    // Set it to the active buffer on the main window
    editor.core.windows.active_mut().select(id);

    // Insert some text into our buffer
    editor
        .core
        .active_buffer()
        .expect("Just set to something")
        .as_text()
        .expect("Should be text buffer")
        .insert(
            "Press `ctrl-c` to exit :), and you'll see a fun message :)",
            &text::CursorOptions::new(),
        );

    println!(
        "We can also access the info here! The value is {}",
        editor.state.my_plugin
    );

    // Actually run the editor
    kwark::run(editor);

    // We get control back afterwards
    println!("Thank you for using kwark!!!");

    Ok(())
}

Let’s explain some more code:

  • The PluginState implementation: Kwark uses this in order to know what data must be stored within your MyState type that uses the macro. We also utilize this in order to have our plugin return a valid initial state in order to create it. This init method is run very early, while creating MyState, and is how we insert all of the important items for our plugin into the editor.
  • The Plugin implementation: Kwark uses this in order to actually do some operation to the Editor when it is registered. This is where we should add things like new commands, event-watchers, and anything else your plugin needs to modify within the editor in order to function well.
  • The #[kwark::state] attribute macro: This attribute macro allows us to modify the MyState type to have the correct trait implementations and function layout that kwark expects in order to run the Editor, without this, we would be unable to run kwark::init::<MyState>()?.
    • The #[plugin(MyPlugin { })] attribute: This attribute forces us to correctly create the plugin type with its info needed to run (just an initializer for the type). This can be any code, so if MyPlugin had a new method, we could use it here instead of the struct definition

State

Your State struct (the #[kwark::state] macro) is the driver for all plugins and custom state you may want within your flavor

If you’re looking for how to install plugins into your state, see plugins.

Inserting custom state

use std::time::Duration;

use kwark::prelude::*;

#[kwark::state]
struct State {
    // Here, we define the **initial** value that is taken when `kwark::init` runs.
    #[default(0)]
    value: i32,
}

fn main() -> anyhow::Result<()> {
    // Most of the code here is similar to that of `minimal.rs`, so we won't be explaining it.
    let mut editor = kwark::init::<State>()?;

    let normal = editor.core.input.tree("normal");

    normal.bind(&["ctrl-c"], "Check Quit", |e| {
        // Here is where some things are different, we are only going to exit the editor **if** we press
        // ctrl-c twice within 0.5 seconds, this way, we don't accidentally do it and forget to save our work
        e.state.value += 1;

        // If we **haven't** reset the state here, and it's 2 (double-press of ctrl-c), then we'll quit the editor
        if e.state.value == 2 {
            e.core.running.quit();

            // The editor is exiting, let's not start a timer by exiting early
            return Ok(());
        }

        // We're going to use this again, so let's create it here
        //
        // This function selects and clears all text in the active buffer, and replacees it with the passed text
        fn set_buffer_text(text: &str, e: &mut Editor<State>) {
            // Let's also update our buffer to show some different text!
            let mut primary_buffer = e
                .core
                .active_buffer()
                .expect("`instructions` buffer should be primary")
                .as_text()
                .expect("active buffer should be a text buffer");

            // Go to the 0, 0 position on the buffer (the start of the file)
            primary_buffer.set(0, 0, &text::CursorOptions::new());

            // Select the entire buffer (to the end of the file)
            primary_buffer.goto(
                Some(text::Target::End), // Select to the last line
                Some(text::Target::End), // Select to the last column
                &text::CursorOptions::new().extend(true),
            );

            // Delete the selection
            primary_buffer.delete(&text::CursorOptions::new());

            // Insert our new text
            primary_buffer.insert(text, &text::CursorOptions::new());
        }

        // We'll set the buffers text here
        set_buffer_text("Press ctrl-c 1 more time to exit", e);

        // Register a timer that, after 0.1 seconds, set the value of our state to 0.
        e.core.timers.after(Duration::from_secs_f32(0.5), |e| {
            e.state.value = 0;

            // Reset the buffer text after a delay
            set_buffer_text("Press ctrl-c 2 times to exit", e);
            Ok(())
        });

        Ok(())
    })?;

    let id = editor
        .core
        .buffers
        .insert(text::BufferEntry::new_scratch("instructions"));

    editor.core.windows.active_mut().select(id);

    // Here, let's initialize the buffer's text
    editor
        .core
        .active_buffer()
        .expect("We should have an active buffer")
        .as_text()
        .expect("Buffer should be text")
        .insert("Press ctrl-c 2 times to exit", &text::CursorOptions::new());

    kwark::run(editor);

    Ok(())
}

Now, this above example is pretty complicated, but it’s to show you what’s possible. However, this explanation is only going to talk about what #[default(0)] means, the other piece can be ignored.

The #[default(expr)] format is used when a State element doesn’t come from a plugin. Instead, this is used when the flavor itself wants to use a value for something, and not have any plugins know about it.

Why use this over a plugin

This is where it gets tricky, as in most use-cases, users should never touch #[default], but as seen in the example above, this is a case where maybe a plugin doesn’t make sense. So in other words, you should avoid using #[default] for things that would make more sense as a plugin, IE: something that may or may not be reusable, or something that would make more sense to be abstracted out of the state itself
